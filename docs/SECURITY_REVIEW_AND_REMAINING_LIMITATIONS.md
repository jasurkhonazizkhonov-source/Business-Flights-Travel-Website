### CSP: can `unsafe-inline` go? (measured on the production build, 2026-11-22)

**What the 223 built pages actually inline** (`tests/csp-violations.spec.ts` pins the facts that are stable): 0 inline `<style>` elements, 0 event-handler attributes, 0 `javascript:` URLs, about 5,900 `style="..."` attributes (React style props), 796 JSON-LD data blocks (`type="application/ld+json"`, never executed, not governed by `script-src`), and, as the only executable inline scripts, Next.js's own `self.__next_f.push([...])` flight payloads and its two bootstrap snippets. The flight payload is the page's server-rendered data and **differs on every page**: across the 223 pages there are 1,220 inline executable scripts with **776 distinct bodies; 774 of them occur on exactly one page** and only the two bootstrap snippets are shared.

**Options measured, not assumed** (a browser loaded the real pages with the policy replaced by each candidate; flows: home + newsletter toast, flights form with airport list, contact, destination):

| Candidate | Browser result |
|---|---|
| current (`script-src 'self' 'unsafe-inline'; style-src 'self' 'unsafe-inline'`) | 0 violations; toasts render |
| `script-src 'self'` (no inline) | **30 inline scripts blocked**, page does not hydrate, no toast |
| `style-src 'self'` + `style-src-attr 'unsafe-inline'` | **8 `style-src-elem` violations**: the toast library (Sonner) inserts a `<style>` element when the toaster mounts, so toasts would render unstyled |

**Why a stricter policy is not available without an architectural change:**
* *Nonces* need a per-request value in the header and in every inline script, which Next.js applies only to **dynamically rendered** pages (`node_modules/next/dist/docs/01-app/02-guides/content-security-policy.md`: "you must use dynamic rendering to add nonces"; static optimisation, CDN caching and Partial Prerendering are lost). All 223 pages are statically generated today; making them per-request is a performance and hosting-cost decision, not a header change.
* *Hashes* of the inline scripts cannot be listed in a header because they differ per page and per build; Next.js's experimental SRI hashes only **external** script files, so it does not cover the inline payloads and is marked experimental.
* **Added 2026-11-23: `script-src-attr 'none'`.** `'unsafe-inline'` in `script-src` also allows inline event-handler attributes (`onclick="..."`), which this site never uses (0 on all 223 pages, re-measured). The policy now refuses them, so an injected handler attribute cannot become script; hydration is unaffected (0 violations in the flow experiment; a test proves an injected `onclick` and `onerror` neither run nor go unreported). This does **not** remove the inline-script requirement above: the CSP is still not fully hardened.
* The `style-src` narrowing needs the toast library replaced or reconfigured; that is a small project of its own and is **not** done here.

**Risk the current policy leaves, honestly:** if an attacker could inject markup into a page, an inline `<script>` would run. The site renders no visitor-supplied HTML (every `dangerouslySetInnerHTML` is a JSON-LD data block with `<` escaped), the forms accept text that is escaped on output, and the markup-in-the-location-hint case is tested (it is shown as text). `connect-src 'self'`, `frame-ancestors 'none'`, `base-uri`, `form-action` and `object-src 'none'` still limit what injected script could do (no outbound requests to another origin, no framing, no form retargeting). Recommended future work, in order: replace the toast library with one that does not inject a style element (then narrow `style-src`); consider dynamic rendering plus nonces only if the site starts handling sensitive data.

### Rate limiting and form abuse (reviewed 2026-11-22)

| Where | Limit | Key |
|---|---|---|
| `submitFlightRequest` | 8 per 10 minutes | trusted client IP (IPv6: its /64) |
| `submitContactMessage` | 8 per 10 minutes | same |
| `subscribeToNewsletter` | 6 per 10 minutes | same |
| `GET /api/visitor-hint` | 120 per 10 minutes, then `429` + `Retry-After: 600`, `no-store`, body `{}` (the form simply shows no suggestion) | same; **new in this task**; a request whose client the trusted proxy path cannot identify is not counted |

* **Nature:** one sliding-window counter in this Node process's memory (`src/lib/sliding-window.ts`, shared through `globalThis` so every route bundle in the process uses the same counters). It is checked and updated in one synchronous step, so concurrent requests inside the process cannot slip past it (tested with 500 concurrent callers: exactly the limit gets through).
* **What it does not do:** it is **per process and reset by a restart**. The VPS runs one website container, so that is one counter; a second instance would double the allowance and a restart (every deploy) clears it. It does not stop an attacker with many addresses.
* **Fixed in this task:** (1) an IPv6 visitor was keyed by full address, so one /64 (2^64 addresses) could mint a fresh allowance per request - IPv6 clients are now keyed by /64, which is how a single subscriber or device is normally addressed; (2) memory was only loosely bounded and, above 5,000 live keys, every request scanned the whole table - it is now capped at 50,000 keys with amortised sweeps and hysteresis (tested: 60,000 distinct keys in well under 5 s; the table never exceeds its cap); (3) the visitor-hint route had no limit.
* **Client identification** is the trusted-proxy resolution (`src/lib/client-ip.ts`): a forged `X-Forwarded-For` or an unverified Cloudflare header does not choose a bucket; unidentifiable requests share one fixed bucket (so a flood of unidentifiable requests exhausts only that bucket, and the log says so once per 5 minutes).
* **Other layers, all verified in tests:** server-side re-validation of every field; honeypot and minimum-fill-time checks before the CRM is called; Server Action bodies capped at 64 KB (413 above that); the CRM client's own bounded retries (3 attempts, 10 s each) and the CRM's per-visitor limit (20 requests per 15 minutes on the flight route) plus idempotency (a repeated submission is one lead). So an automated submitter is stopped at the website after 8 accepted submissions per 10 minutes per client, and cannot create more than a bounded number of CRM calls per client; **a botnet with many addresses is limited only by the CRM's per-visitor limit and by how many distinct visitors it can fake.**
* **What would be reliable:** a Cloudflare rate-limiting rule on the edge (the control that is shared across instances and survives restarts). Recommended rule, **not applied** (a Cloudflare change needs your approval): *When* Request Method equals `POST` **and** the request has a `Next-Action` header (that header is what marks a Server Action call; the site's three actions are its only POST endpoints), *rate* 12 requests per 10 minutes per IP, *action* Block for 10 minutes (or Managed Challenge); and, as a second rule, URI Path equals `/api/visitor-hint`, 150 requests per 10 minutes per IP. Verify after enabling by submitting the form once (must succeed) and by checking the rule's event log; roll back by disabling the rule. Cloudflare's free plan limits how many rules and which characteristics are available; check the current plan before relying on this.
* **CAPTCHA:** none, and none was added (a third-party challenge changes the visitor journey and needs your decision). Assessment for the intended deployment: **sufficient for launch** given the layers above and a single container, **not sufficient** against a determined distributed spammer, who would produce junk CRM leads. If junk appears, the smallest compatible step is Cloudflare Turnstile (free, privacy-preserving, invisible by default). Decisions needed first: use Turnstile or not; where the secret key is stored (a new server variable, never in Git); the Content-Security-Policy would need `https://challenges.cloudflare.com` in `script-src`, `frame-src` and `connect-src` (a deliberate widening); and the exact failure message shown to a visitor who fails the challenge.

## 6. Visitor IP and geolocation privacy

One implementation resolves the visitor: `src/lib/client-ip.ts` (trusted-proxy modes; `TRUSTED_PROXY=cloudflare` reads only `cf-connecting-ip`, and `cf-connecting-ipv6` only for Cloudflare's pseudo-IPv4 stand-in; forwarded-for style headers are ignored in that mode; private/loopback/CGNAT/Docker/reserved addresses are "unavailable"). The visitor hint and the CRM capture both use it. Verified by tests on real servers: untrusted Cloudflare-looking headers are not believed; the hint response contains no IP/coordinates; device coordinates never leave the browser; the hint is not cacheable across visitors; missing or malformed headers give a safe empty answer; logs carry no IP. **Residual:** the application cannot prove a request came through Cloudflare; the protection is the topology (no published port, enforced by `deploy/preflight.sh`), so that preflight and the Docker rehearsal are release gates.

**The trust boundary, stated exactly (reviewed 2026-11-22).** With `TRUSTED_PROXY=cloudflare` (fixed by `compose.yaml`, not configurable from `.env`), the application believes `CF-Connecting-IP` (and Cloudflare's country/coordinate headers) **and nothing else**: `X-Forwarded-For`, `X-Real-IP` and `Forwarded` are ignored, and the same Cloudflare-looking headers are **not** believed when no trusted proxy is configured or when the proxy is another kind (tests on real servers). Cloudflare overwrites `CF-Connecting-IP` on every request it proxies, so a visitor cannot choose it **provided the request really came through Cloudflare**. What guarantees that is the topology, and it has these properties:
* **No host port is published** (`compose.yaml` has no `ports:`); `deploy/preflight.sh` refuses a rendered configuration that publishes one and `deploy/verify.sh` re-checks the running container (`docker port` must be empty). So the origin is not reachable from the internet or the LAN; only containers on a Docker network the website joined can reach `bft-web:3000`.
* The website joins two external networks: the CRM's **internal** API network and the tunnel network (`compass-tools_web`). Whatever else sits on the tunnel network **can** reach the origin directly and could send a forged `CF-Connecting-IP`; in the CRM's release `compose.yaml` the `web` network carries `cloudflared`, the CRM `app` and the CRM's `cvv-cleanup` job container (the live stack's layout was not inspected). A compromised CRM container could therefore forge visitor addresses on the website; it already holds the CRM, so this adds no new capability, but **do not attach any other service to that network** without re-reading this paragraph. The preflight also refuses a database container on either network and a second container answering to `bft-web`.
* Cloudflare Tunnel connects outward from the VPS, so there is no inbound port to protect. **Not verified from this machine:** that no firewall rule, reverse proxy or second tunnel route points at the origin by another path, and that the tunnel's public hostname is the only route. That is part of the read-only Cloudflare/VPS inspection in the runbook (section E and step 0).
* If the trust assumption fails, the effect is bounded: a forged address changes which rate-limit bucket a client uses, which IP/location the CRM records for that lead, and which airport is suggested to that visitor. It cannot bypass the CRM's authentication (the signing secret never leaves the server) and it does not expose another visitor's data. Raw addresses are **not** returned by any public route and are not logged (the logs say only "captured" or the value-free reason it was unavailable); they reach the CRM only inside the signed envelope, and the business's own notification e-mail.

### Server Action origin check and hostile requests (2026-11-22)

Full findings, probes and the list of verified negatives: `FINAL_CODEBASE_AUDIT_2026-11-22.md`. In short: a cross-origin Server Action call with a real action id (`Origin: https://evil.example`, `null`, or a mismatched site) is refused by Next's origin check before the action runs; a request with **no** `Origin` header is accepted and a non-browser client that also forges `X-Forwarded-Host` passes the check, which matters little because a browser cannot set that header cross-site without a failing CORS preflight and the site has no cookies or sessions to ride on (the actions are public by design and protected by the per-IP limit, honeypot, idempotency and the CRM's own limit). The image optimizer refuses every SSRF and parameter-abuse variant tried (non-allow-listed hosts, loopback, link-local metadata, userinfo and prefix tricks, `file:`, traversal, widths and qualities off the allow-list); `//host` and encoded-slash paths never become an off-site redirect; nothing outside `public/` is served; a forged `Host`/`X-Forwarded-Host` is never written into any page, canonical URL, sitemap or robots.txt; malformed Server Action bodies get a bare `409 Server Action unavailable.` with no stack or path. Pinned by `tests/http-boundaries.spec.ts`.

### Clock synchronisation (signing v2)

The CRM accepts a request only if its signed timestamp is **at most 120 s old and at most 30 s ahead** of the CRM's own clock (`WEBSITE_SIGNATURE_MAX_AGE_SECONDS = 120`, `WEBSITE_SIGNATURE_MAX_FUTURE_SECONDS = 30` in the CRM's `website-request-signature.ts`; read for this review, not modified), and accepts each nonce once (kept until the timestamp's 120 s plus 60 s have passed). The website generates a fresh timestamp and nonce for **every attempt**, so a retry is never "stale". Verified behaviour (`tests/crm-api-client.spec.ts`, stand-in CRM enforcing the same numbers): 100 s behind and 20 s ahead are accepted; 150 s behind (`expired`) and 45 s ahead (`future`) are refused with 401; a replayed envelope (`replay`) is refused; a wrong secret is refused; each refusal is **not retried** and is never reported to the visitor as success (the visitor sees the generic error).
* **Both servers need a synchronised clock.** A website server that drifts more than ~30 s *ahead* of the CRM, or a CRM clock more than 120 s ahead of the website's, makes **every** enquiry fail while health checks stay green. Enable NTP on both (`timedatectl status` must show `System clock synchronized: yes`).
* **Diagnosis:** the CRM logs `[website-signature] refused: <reason>` with the reason `expired`, `future`, `replay`, `bad_signature` or `malformed`; the website logs `the CRM refused the website's credential or route (HTTP 401)` and names the variables to check. `expired`/`future` together with a clock difference = clock drift; `bad_signature` = different `LEAD_INGEST_SECRET` (or company id) on the two sides; `replay` = a duplicated request (a proxy or script resending the same envelope).
* **Safe remedy:** fix the clock (NTP) or the mismatched secret. **Do not widen the window** to hide drift: a wider window lengthens how long a captured envelope can be replayed and is not needed by correct clocks. Compare `date -u` on both hosts and `docker exec <container> date -u` on each side; compare the website's and CRM's UTC seconds, not their time zones.

## 9. Cloudflare Email Address Obfuscation: is switching it off necessary?

What it does: Cloudflare rewrites each `mailto:` and visible address into `/cdn-cgi/l/email-protection#<hash>` and decodes it with a script. Search Console reported the bare `/cdn-cgi/l/email-protection` as a 404. The website source contains plain `mailto:` links; the rewriting happens at the edge (verified in the live HTML).
Assessment: **optional, low priority.** (a) The report is informational and has no ranking effect; `robots.txt` now disallows `/cdn-cgi/`. (b) The privacy benefit is small: the business address is already public in the site's `TravelAgency` JSON-LD and on the contact page, which are not obfuscated. (c) The cost of leaving it on: visitors without JavaScript cannot see the address, and the URL keeps appearing in Search Console. (d) The cost of switching it off: the address becomes plain text in the HTML for scrapers (it already is in JSON-LD). Alternatives: leave it on and ignore the report; or wrap specific addresses in `<!--email_off-->` comments. **Not changed; your decision.**
