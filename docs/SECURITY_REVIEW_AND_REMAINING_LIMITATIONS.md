# Security review and remaining limitations

Date: 2026-11-20 (continuation task). Scope: the website in `F:\Claude Workspace\Travel Agency Website-updated`, branch `review/website-parity-and-contact-ip-2026-11-15`. Evidence: the source, `npm audit`, the production (standalone) build, the Playwright suites, and read-only public GETs of the live site. **Nothing was deployed, no production setting was changed, the CRM was not modified.** This document is public-safe: it contains no secret, customer data or server address, and it lists weaknesses in general terms only where an attacker could not use the text as a map beyond what the code already shows. It is a review by the engineer who made the changes, not an independent penetration test, and makes no compliance claim.

## 3. Security headers (verified on the production build)

| Header | Value | Assessment |
|---|---|---|
| Content-Security-Policy | `default-src 'self'; script-src 'self' 'unsafe-inline'; style-src 'self' 'unsafe-inline'; img-src 'self' data:; font-src 'self' data:; connect-src 'self'; frame-ancestors 'none'; base-uri 'self'; form-action 'self'; object-src 'none'` (dev adds `unsafe-eval` and localhost websockets only) | No third-party origin anywhere (tested: no `http(s)://` and no `*`). **Limitation:** `'unsafe-inline'` for scripts and styles, because Next.js hydration and the inline JSON-LD blocks need inline scripts and no per-request nonce is wired through; that weakens XSS mitigation. The site has no user-supplied HTML and no `dangerouslySetInnerHTML` except escaped JSON-LD, so the practical risk is low. A nonce-based CSP is a real project (middleware + every inline script) and was deliberately not bolted on here |
| X-Frame-Options / `frame-ancestors` | `DENY` / `'none'` | clickjacking refused twice over |
| X-Content-Type-Options | `nosniff` | ok |
| Referrer-Policy | `strict-origin-when-cross-origin` | ok |
| Permissions-Policy | `camera=(), microphone=(), geolocation=(self), payment=(), usb=(), interest-cohort=()` | geolocation for this site's own pages only; since framing is refused, no third-party frame can inherit it |
| Strict-Transport-Security | **`max-age=63072000` (two years, this host only)**. **Changed in this task:** the previous value also sent `includeSubDomains; preload` | `includeSubDomains` binds every subdomain of the domain to HTTPS-only and `preload` makes the domain eligible for the browsers' built-in list (very hard to undo); nothing in this repository can confirm that every subdomain is HTTPS-only or that the owner wants that. Add them later only as a deliberate decision, then submit to the preload list |
| X-Powered-By | absent | ok |
| Cache-Control | `/api/visitor-hint`: `private, no-store`; pages are static or per-request; no sensitive page is cacheable by a shared cache | ok |
| CORS | no `Access-Control-*` header on any route (tested with a foreign `Origin`) | the site is not an API for other origins |

`tests/security-headers.spec.ts` (new) pins all of the above on 11 pages, the 404 page and the route handlers. **Finding recorded by that test:** the app's own `308` redirects (for example `/terms`) carry **none** of these headers, because Next.js answers a `redirects()` rule before it applies `headers()`. A redirect has no body to frame, sniff or inject into, and HSTS is learned from the 200 responses that follow, so this is a low-impact limitation, not a defect worth working around; the test asserts only the redirect target, no cookie and no framework banner. Cloudflare's own redirect (the apex rule) is separate and may add its own headers.

## 4. Cookies and browser storage (complete inventory)

| Storage | Key | Content | Set when | Sensitive? |
|---|---|---|---|---|
| Cookies | none set by this site (verified: no `Set-Cookie` on any tested response; `document.cookie` empty). Cloudflare may set its own cookies at the edge; that is outside this repository | - | - | - |
| `localStorage` | `bft-cookie-consent` | `{version, decidedAt, preferences}` (the visitor's cookie-notice choice) | when the visitor answers the notice | no; must be readable by script (not a candidate for HttpOnly) |
| `sessionStorage` | ~~`bft-geolocation-declined`~~ | a flag that the location prompt was refused | **removed in this task** | - |

The `sessionStorage` flag introduced with the location suggestion was **removed**: browsers remember a refusal themselves and report it through the Permissions API, which the hook already reads on every page load, so the flag was redundant. A test models that browser behaviour and asserts that nothing about the refusal is stored (no session storage entry, no location-related local storage key, no cookie). This also makes the Cookie Policy's statement that the forms need no browser storage fully accurate again. No session cookie, authentication cookie or CSRF cookie exists (the forms are Server Actions, which carry Next.js's own origin checks).

## 5. API and form security

| Surface | Controls verified (tests in brackets) |
|---|---|
| Flight request (Server Action) | server-side schema re-validation of every field including the 11-month date window, email and phone; honeypot and minimum-fill-time checks; per-client in-memory rate limit keyed on the trusted client IP; body capped at 64 KB (`server-action-body-limit-e2e`); a signed (v2) request to the CRM, never unsigned; idempotency key; fixed visitor messages, no CRM detail, no stack trace; the form keeps its input on any failure |
| Contact (Server Action) | same validation, honeypot, rate limit; one attempt, no automatic retry; signed |
| Newsletter (Server Action) | email validation (browser/server share one rule set, a subset of the CRM's); honeypot; rate limit; signed; **no enumeration**: the answer is the same whether or not the address is already subscribed (`alreadySubscribed` is always false) |
| `GET /api/visitor-hint` | GET only (405 on POST/PUT/PATCH/DELETE, tested); returns only a country code and an airport; no IP, no coordinates; read only behind the declared trusted proxy; `private, no-store`; junk headers produce an empty answer |
| `GET /api/health` | no application detail; `noindex` |
| Route handlers overall | only `health`, `visitor-hint` and the `brand-mark.png` image exist; no write endpoint, no file upload, no user-controlled outbound request (the only `fetch` calls are same-origin and the configured CRM URL), no redirect built from user input |

CRM contract preserved (not weakened): signature v2 binds method, path, company, exact body, timestamp and one-time nonce; 120 s past / 30 s future; nonce store failure is a 503; v1 and unsigned requests are rejected by the CRM; the website signs each retry afresh and never falls back to unsigned. Secrets reach neither the browser nor the logs (tested).

Abuse protection, honestly: the website's own limiter is **in memory** (per instance, reset on restart) and the CRM adds a shared per-visitor limit on the flight route; there is no CAPTCHA and none was added (an external service needs your approval). Distributed spam from many IPs, or a bot that reads the form's timing, is only slowed, not stopped; the honeypot and timing checks catch only unsophisticated bots. If real spam appears, the smallest compatible step is a free challenge service in front (Cloudflare Turnstile) - a decision for you.

## 6. Visitor IP and geolocation privacy

One implementation resolves the visitor: `src/lib/client-ip.ts` (trusted-proxy modes; `TRUSTED_PROXY=cloudflare` reads only `cf-connecting-ip`, and `cf-connecting-ipv6` only for Cloudflare's pseudo-IPv4 stand-in; forwarded-for style headers are ignored in that mode; private/loopback/CGNAT/Docker/reserved addresses are "unavailable"). The visitor hint and the CRM capture both use it. Verified by tests on real servers: untrusted Cloudflare-looking headers are not believed; the hint response contains no IP/coordinates; device coordinates never leave the browser; the hint is not cacheable across visitors; missing or malformed headers give a safe empty answer; logs carry no IP. **Residual:** the application cannot prove a request came through Cloudflare; the protection is the topology (no published port, enforced by `deploy/preflight.sh`), so that preflight and the Docker rehearsal are release gates.

## 7. Input, output and browser security

No `dangerouslySetInnerHTML` except JSON-LD, which is escaped (`<` becomes `\u003c`); editorial content is data rendered through React elements and a link syntax that produces anchors, not HTML; every external link carries `rel="noopener noreferrer"` (the two Trustpilot links also `nofollow`); there is no open redirect, no path handling from user input, no database access by the website (no SQL), no file handling. Server-rendered error pages show fixed text.

## 8. GitHub and release workflow

There is **no CI**: no `.github/workflows`, so no automated build, test, Docker rehearsal or deployment exists, and a push cannot deploy anything. Deployment is a manual, scripted procedure on the VPS (`deploy/preflight.sh`, `deploy/deploy.sh`, `deploy/rollback.sh`; runbook in `WEBSITE_VPS_DEPLOYMENT_AND_ROLLBACK_RUNBOOK.md`), which refuses a dirty working tree. A workflow was **not** added: a new CI file is a repository-configuration change that cannot be tested here and, for the browser and Docker jobs, needs runner choices (paid minutes, permissions) that are yours to make. If you want one, the minimal safe shape is: `on: pull_request` and `push` to the working branch, `permissions: contents: read`, no secrets, actions pinned to commit SHAs, jobs for `npm ci`, `tsc`, `eslint`, `next build` and the unit/SEO specs, **no deploy job**.

## 9. Cloudflare Email Address Obfuscation: is switching it off necessary?

What it does: Cloudflare rewrites each `mailto:` and visible address into `/cdn-cgi/l/email-protection#<hash>` and decodes it with a script. Search Console reported the bare `/cdn-cgi/l/email-protection` as a 404. The website source contains plain `mailto:` links; the rewriting happens at the edge (verified in the live HTML).
Assessment: **optional, low priority.** (a) The report is informational and has no ranking effect; `robots.txt` now disallows `/cdn-cgi/`. (b) The privacy benefit is small: the business address is already public in the site's `TravelAgency` JSON-LD and on the contact page, which are not obfuscated. (c) The cost of leaving it on: visitors without JavaScript cannot see the address, and the URL keeps appearing in Search Console. (d) The cost of switching it off: the address becomes plain text in the HTML for scrapers (it already is in JSON-LD). Alternatives: leave it on and ignore the report; or wrap specific addresses in `<!--email_off-->` comments. **Not changed; your decision.**
