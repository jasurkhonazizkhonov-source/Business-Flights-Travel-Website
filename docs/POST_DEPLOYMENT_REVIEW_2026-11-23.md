## 1. Security

| # | Item | Class | What the code shows today | What closes it |
|---|---|---|---|---|
| 1 | **CRM signature enforcement** (`WEBSITE_SIGNATURE_REQUIRED`) | **Partially resolved; the last step requires owner approval** | The website signs **every** CRM request with signature v2 (`src/lib/crm-api/visitor-context.ts`): HMAC-SHA256 with `LEAD_INGEST_SECRET` over a length-prefixed message of method, path, company id, timestamp, one-time nonce, SHA-256 of the exact body and the visitor-context header; each retry gets a fresh timestamp and nonce with the same Idempotency-Key. The CRM verifies it (`website-request-signature.ts`: 120 s past / 30 s future, nonce stored once, constant-time comparison, previous-secret rotation). **Current CRM behaviour is transitional** unless `WEBSITE_SIGNATURE_REQUIRED=true`: a valid v2 signature is verified and used, but **unsigned and v1 requests are still accepted**; strict mode refuses them with 401. The website's preflight refuses to deploy without the secret (unless `PREFLIGHT_ALLOW_UNSIGNED=yes`), but a deployed container with the variable missing would send unsigned. I did not enable strict mode, change any variable or rotate anything | Owner: confirm signed requests verify in production (CRM log shows no `[website-signature] refused`), then set `WEBSITE_SIGNATURE_REQUIRED=true` on the CRM and restart it; rotation via `LEAD_INGEST_SECRET_PREVIOUS`. Procedure: runbook sections Q, J |
| 2 | **Rate limiting** (per-process; visitor hint) | **Accepted limitation; edge rule requires owner approval** | One in-memory sliding window per process (`src/lib/sliding-window.ts`), IPv6 by /64, memory-capped, synchronous check-and-update. Forms: 8 / 8 / 6 per 10 minutes per client. **`/api/visitor-hint` is now far cheaper to hit**: it returns only `{countryCode}` (the airport lookup and its dataset read are gone; the coordinates the platform may send are no longer used at all), and still answers 429 after 120 per 10 minutes per identified client. Abuse risk assessment: the hint route cannot be used for anything harmful or expensive; the real cost centres are the three Server Actions (validation, then an outbound CRM call), limited per client by the website, per visitor by the CRM (20 per 15 minutes on the flight route), and bounded by the 64 KB body cap and idempotency. The limiter resets on every deploy/restart and is not shared across instances, so a determined multi-address attacker is limited only by the CRM. **A Cloudflare rate-limiting rule is still advisable** as defence in depth (runbook E4); it is not a launch blocker for a single container | Owner approval for the edge rule |
| 3 | **Trusted client IP** (`CF-Connecting-IP`, forwarded headers, Docker networks, CRM) | **Requires external infrastructure / owner (live inspection)** | Code: only `CF-Connecting-IP` (and Cloudflare's own geo headers) are believed when `TRUSTED_PROXY=cloudflare`; `X-Forwarded-For`, `X-Real-IP`, `Forwarded` are ignored; the same headers are **not** believed with no trusted proxy (tests on real servers). **Who could forge it:** a client cannot, if every request really arrives through the tunnel (no host port is published; preflight and verify refuse one). A **container on the tunnel network** can reach `bft-web:3000` directly and send any `CF-Connecting-IP`; in the CRM's release compose that network carries `cloudflared`, the CRM app and its `cvv-cleanup` job. A forged value only changes a rate-limit bucket and the IP/location recorded for that lead; it cannot bypass CRM authentication. Not verified: the live VPS networks and any second route to the origin. I changed no topology | Read-only inspection on the VPS (runbook step 0); never attach another service to the tunnel network |
