# SEO technical verification - release candidate

Date: 2026-11-20. Branch `review/website-parity-and-contact-ip-2026-11-15` (uncommitted working tree). Evidence: the local production (standalone) build served on 127.0.0.1:3101, `scripts/validate-seo.mjs`, `scripts/audit-seo-inventory.mjs`, the Playwright suites, and read-only public GETs of the live site for comparison. **Nothing was deployed.** "Lab" numbers are not field data; no Core Web Vitals from real users were available.

## 1. Route inventory (baseline 218 -> 223)

| Kind | Count | Notes |
|---|---:|---|
| Static pages | 11 | home, `/flights`, `/business-class`, `/destinations`, `/how-it-works`, `/about`, `/blog`, `/contact`, `/privacy-policy`, `/cookie-policy`, `/terms-of-service` |
| Region hubs (new) | 5 | `/destinations/europe`, `/asia`, `/africa`, `/middle-east`, `/oceania` (regions with 9+ destinations; North and South America have 2 and 5 and stay sections of `/destinations`) |
| Destination pages | 171 | `/destinations/<region>/<country>/<city>` |
| Articles | 36 | `/blog/<slug>` |
| **Sitemap URLs** | **223** | all unique, all on `https://www.businessflights.travel` |

`validate-seo`: **223 routes, 0 failures** (HTTP 200, no redirect, self-canonical, no `noindex`, one H1, title and description present, sitemap membership, robots). Inventory audit: 0 non-200, **0 duplicate titles, 0 duplicate descriptions, 0 duplicate H1s**, 0 broken internal links, every route reachable from the home page, maximum depth 2 clicks. (A duplicate title between the Africa hub and the Africa planning article was found by the audit and fixed before this verification: hubs are now titled "Business-Class Destinations in X".)

## 2. Canonicals

* Every indexable route: exactly one `<link rel="canonical">`, equal to its own production URL. Checked on all 223 routes (the sitemap and the canonicals use the same hostname).
* `/flights?to=XXX` (58 reported URLs, and any other value): canonical `/flights`; the clean destination page is the one meant to rank. No canonical chains, none pointing at a redirect, a 404, or the home page.
* `og:url`, Twitter and JSON-LD URLs agree with the canonical (`pageMetadata` builds them from one path; the destination and hub pages build theirs from `destinationPath` / `/destinations/<region>`).

## 3. robots.txt

Live today (read-only): `User-Agent: *`, `Allow: /`, `Disallow: /api/`, `Sitemap: https://www.businessflights.travel/sitemap.xml`.
This build: the same plus **`Disallow: /cdn-cgi/`** (Cloudflare's namespace on this host; its email-address obfuscation links to `/cdn-cgi/l/email-protection`, which Google reported as a 404). Nothing indexable is blocked: blog, destinations, flights, the CSS/JS under `/_next/` and all pages stay open (`tests/seo.spec.ts`, two tests).

## 4. Sitemap

223 `<loc>` entries: 11 static + 5 hubs + 171 destinations + 36 articles. Excluded and tested: query URLs (`?to=`), redirected URLs (`/terms`, the retired blog slugs), 404 URLs (`/offers`), assets and image endpoints (`/twitter-image`, icons, manifest), anything under `/api/`. `lastmod`: **not emitted for static pages, hubs and destinations** (no real per-page modification tracking exists; stamping every URL "now" on each deploy is the anti-pattern Google warns about); **emitted for articles** from `updatedAt`, a hand-maintained date, which this pass advanced to 2026-11-20 only for the ten articles that really changed.

## 6. Metadata

Titles, descriptions and H1s are unique across all 223 routes (inventory audit). Open Graph and Twitter tags are generated by one function (`pageMetadata`) or, for destinations and hubs, the equivalent in `generateMetadata`; the share images are the branded `opengraph-image`/`twitter-image` routes (served as images, excluded from the sitemap). Destination titles longer than 62 characters drop the brand suffix (existing rule).

## 7. Structured data

| Page kind | JSON-LD types (all valid JSON, none duplicated) |
|---|---|
| Every page (layout) | `TravelAgency` (with `ContactPoint`, `PostalAddress`), `WebSite` |
| Home | + `FAQPage` |
| Static pages, `/destinations`, region hubs | + `BreadcrumbList` |
| Destination pages | + `BreadcrumbList` (Home > Destinations > Region hub > City; 3 items where the region has no hub), `FAQPage` where the page has FAQs |
| Articles | + `Article` (headline, image, `datePublished`, `dateModified`, author = the Editorial Team organisation, publisher), `BreadcrumbList`, `FAQPage` where the article has FAQs |

BreadcrumbList is on **222 of 223** routes (home excluded by design, no crumb below it). Checks: no `#fragment` in any breadcrumb item (tested for all 171 destinations); no invented ratings, reviews, prices or offers anywhere; every marked-up FAQ is visible text on the page. Note: Google stopped showing FAQ rich results in May 2026, so `FAQPage` markup no longer buys a rich result; it is accurate, harmless and was left in place.

## 8. Internal linking

Hierarchy: Home -> Destinations -> **Region hub** -> country section -> city. Every destination page is linked from the destinations index, from its region hub (if it has one), from related-destination blocks, and from articles where relevant. Incoming internal links per destination page: min **4** (was 3), median **6** (was 5). Articles: related links plus guides on destination pages. The 58 `/flights?to=` links stay as the quote call to action (canonical `/flights`).

## 9. Rendering and crawlability

The page content is in the server-rendered `<main>` (no loading fallback, no content swapped in by a script: tested on the home page, an article, a destination and a hub); `Reveal` leaves the first screen exactly as rendered (documented in the component); breadcrumbs, links, metadata and JSON-LD are in the initial HTML; hub and destination pages work without JavaScript for content discovery. No page requires a click before its text appears.

Reading: CLS is 0 everywhere. Text pages are fast. The LCP element on articles, destinations and the destinations index is the hero/card image; those exceed the 2.5 s "good" threshold under this harsh emulation. The hero images already carry `priority`/`fetchPriority="high"` and correct `sizes`, are served as WebP (24 KB at 384 px, 134 KB at 1080 px), and `Reveal` does not hide them, so there is **no defect identified that a blind code change would fix safely**. Candidates for a measured follow-up on real hardware (Lighthouse or PageSpeed Insights against the deployed site, then CrUX once data exists): lower image quality for the darkened hero overlays, trimming `/destinations` (171 cards, 2,855 DOM nodes, TBT about 1.5 s). `/offers` was not measured (404). The earlier finding that the local standalone copy served images *unoptimised* was a property of the test layout (sharp's libvips missing), not of the Docker image; the Dockerfile copies the full `@img` packages.

## 11. Post-deployment Search Console checklist (nothing here is automated; none of it guarantees indexing)

1. Confirm the deployed canonical host: `https://www.businessflights.travel`, and that `http(s)://businessflights.travel` redirect to it.
2. Open `https://www.businessflights.travel/sitemap.xml`: 223 URLs, all `https://www...`.
3. Submit (or resubmit) the sitemap.
4. URL Inspection on a handful of representative URLs: the home page, `/destinations/europe`, one destination (e.g. Munich), one expanded article.
5. Check the rendered HTML and the selected canonical in the inspection result.
6. Confirm no `noindex` and that robots.txt now shows `Disallow: /cdn-cgi/`.
7. Request indexing for a **small** number of high-priority corrected pages only (hubs, a few featured destinations, the expanded articles). Do not mass-submit.
8. Re-check the indexing report after Google has re-crawled (days to weeks): the "noindex" and "404" groups should drain; "Discovered" depends on Google's crawl scheduling.
9. Watch for new errors (soft 404, canonical conflicts) after the hubs and redirects go live.
10. Record the date of deployment so later changes can be compared.

## 12. What was NOT verified

Real-user Core Web Vitals; Lighthouse itself; Google's own rendering of the pages (URL Inspection needs the deployed site and Search Console access); whether Cloudflare's settings match the recommendations (not inspected); search demand and rankings. None of these can be checked from this machine.


## 13. Post-upgrade verification (Next.js 16.4.6, headers and layout, 2026-11-20)

Re-verified on the final production build after the dependency upgrade and the last source change:

* `validate-seo`: 223 routes, 0 failures. Inventory audit against the local build: 0 non-200, 0 duplicate titles, descriptions or H1s, 0 broken internal links, max depth 2, every route reachable from home (the five region hubs included). The audit's 3 "problems" are the decorative `alt=""` background photo on `/`, `/about`, `/business-class`, which is correct HTML for a decorative image.
* Unchanged by the upgrade: canonicals, `robots.txt` (`Disallow: /api/` and `/cdn-cgi/`), the 223-URL sitemap, the three permanent redirects, real 404s for `/offers` and unknown articles (`tests/seo.spec.ts`, 40 tests, passing on Desktop and the three mobile widths and on the tablet width).
* **Header change with an SEO relevance:** `Strict-Transport-Security` is now `max-age=63072000` only. `includeSubDomains` and `preload` were removed on purpose (they bind every subdomain and make the domain eligible for the browsers' built-in list; neither is an SEO requirement). If you later want them, confirm every subdomain is HTTPS-only first.
* **Layout:** the departure-field helper button no longer shifts the form between roughly 768 and 1023 px (layout shift 0.0064 -> 0 in a 25-run probe); the form's position is stable from first paint, which is the only layout-shift source found on `/flights`.
* **Redirect responses:** the app's own 308s do not carry the security headers (Next.js applies `headers()` only to pages), which has no search effect.
* Lab performance numbers in section 10 were measured on the 16.4.2 build; the upgrade is a patch-level change within the same major and no template, image or script changed, so they were not re-measured and should not be read as a before/after of the upgrade. Real-user data is still required (section 12).
