# Visitor IP address and approximate location — how it works, what limits it, what to check

Written 2026-11-08 from the code in this repository and the CRM's repository at `origin/main` (read only). Nothing here was verified against the live deployment, the live Cloudflare settings or the live CRM.

## Path of the data (flight request)
1. Cloudflare adds `CF-Connecting-IP` (the client address Cloudflare saw). With the *Add visitor location headers* Managed Transform it also adds `cf-ipcity`, `cf-region`, `cf-region-code`, `cf-timezone`, `cf-iplatitude`, `cf-iplongitude`, `cf-postal-code`; with only *IP geolocation* it adds `cf-ipcountry`.
2. `compose.yaml` fixes `TRUSTED_PROXY=cloudflare` (the origin is reachable only through the tunnel). `src/lib/client-ip.ts` reads `CF-Connecting-IP` only (plus `CF-Connecting-IPv6` in the one Pseudo-IPv4 case below), validates it, rejects private/reserved values, canonicalises IPv6 (lower case, zero-compressed), collapses IPv4-mapped IPv6, drops ports and zone ids. `X-Forwarded-For`, `X-Real-IP`, `Forwarded` and `True-Client-IP` are never read in this mode.
3. `src/lib/ip-geo.ts` reads city, region, country, time zone and — as a valid pair, rounded to about 1 km — latitude/longitude from the `cf-*` headers (never postal or metro code), only in `cloudflare` mode.
4. `src/lib/crm-api/visitor-context.ts` signs `{v, ts, ip?, city?, region?, country?, timezone?}` with `LEAD_INGEST_SECRET` and sends it as `x-ct-visitor-context` / `x-ct-visitor-signature` with the flight request. The same data goes into the internal notification e-mail ("Cloudflare edge geolocation (approximate)").
5. The CRM verifies the signature (5-minute window), re-validates the IP, stores `ipAddress` (a plain string — no length limit, IPv6 fits), `ipVersion`, city, region, country, country code, time zone.

## Geolocation provider evaluation (2026-11-08) — decision: no external provider added
Authorised to add one "if necessary"; it is **not** necessary on the evidence, and adding one has real costs.
* **Cloudflare already supplies the needed fields** for every request that reaches the site through it: country (`cf-ipcountry`, needs *IP geolocation* or the Managed Transform), and with *Add visitor location headers*: city, region and region code, time zone, latitude, longitude (also continent, metro and postal codes, deliberately unused). They are free, in the request itself, add no latency or failure mode and send no visitor IP to anyone else. What Cloudflare does **not** give: accuracy radius/confidence, ISP/organisation, a "VPN/relay" flag.
* **The missing city in a CRM lead is therefore a configuration question** (the Managed Transform is off, or `LEAD_INGEST_SECRET` differs between the website and the CRM), not a data-quality limit — and an external provider would not fix the second cause at all.
* **An external provider would send every visitor's IP address to a third party** at submission time: a new sub-processor, a privacy-policy disclosure, a data-processing agreement, retention/logging terms to read, a new secret (kept in the environment, never in the client bundle), a timeout and a failure path on the request that creates a lead. Its answer for the same IP is the same kind of estimate (and for a privacy relay it describes the relay).
* **If a fallback is ever wanted** (for example the Managed Transform cannot be enabled on the plan): prefer a **locally queried database file** on the server (no visitor IP leaves the machine; needs a licence and periodic updates and is a new dependency) over a web API; if a web API is chosen, it must be called from the server only, with a short timeout (≈1.5 s), a circuit breaker, no retry on the lead path, rate-limit handling, the key in an environment variable, and the IP/location left unavailable (never fabricated) on any failure. Provider names, prices, free-tier limits and terms change often and were **not** checked; they must be reviewed at decision time. Nothing was installed, no key requested, no request made to any provider.
* The failure-handling tests listed for a provider (timeout, error, rate limit, unavailable) therefore do not apply; the equivalent behaviour that does exist is tested: no location headers, missing city, missing or partial coordinates, Tor/unknown country, missing IP.

## Suggestions in the forms (departure airport, phone country code)

Separate from what is recorded for the CRM: the forms may pre-fill a **phone country code** and a **departure airport** from the visitor's approximate location, through `GET /api/visitor-hint` (`src/app/api/visitor-hint/route.ts`, `src/lib/visitor-hint.ts`).

* It reads the same trusted-proxy location headers as the capture above and **only** behind the declared trusted proxy (`TRUSTED_PROXY=cloudflare` in the VPS compose); with no trusted proxy it answers `{}`.
* It returns **a country code and nothing else** (for the phone-number prefix): no airport, no city, no coordinates, no IP address. It is `Cache-Control: private, no-store` and logs nothing about the visitor. (Until 2026-11-23 it also returned a nearest-airport suggestion derived from Cloudflare's approximate position; that was removed, because the departure airport is now suggested only from the visitor's own device location, only if they allow it, and a network-derived airport would be a suggestion they had refused.)
* The **country code** works with Cloudflare's free "IP Geolocation" (`cf-ipcountry`). The "Add visitor location headers" Managed Transform is **not needed for any suggestion any more**; it still supplies the city, region, time zone and coordinates that are recorded with a submission (above).
* The **device's own location** (browser Geolocation API) is the only source of the departure-airport suggestion: the browser asks for permission when the flight request page (`/flights`) opens, or, on the home page, when the visitor first uses the form; if they allow it, the coordinates are turned into the nearest major airport **inside the browser** and are never sent anywhere or stored. Full rules, tests and limits: `DEVICE_LOCATION_DEPARTURE_AIRPORT.md`. The `Permissions-Policy` header allows `geolocation` for the site's own pages only (`geolocation=(self)`).
* A suggestion is only a pre-filled form value that the visitor can change, and it is never recorded as the visitor's location; the airport the visitor finally submits is the only trace.

## 6. Optional edge proof (`EDGE_PROOF_SECRET`): who can forge `CF-Connecting-IP`, and the code-level answer (2026-11-23)

**The assumption this site makes.** `TRUSTED_PROXY=cloudflare` (fixed in `compose.yaml`) means: *the origin is reachable only through Cloudflare's tunnel*, so `CF-Connecting-IP`, `CF-IPCountry` and `CF-IPCity` can be believed. That is a property of the **network**, not of the request. Nothing in the request itself says it came through Cloudflare.

**Who could break the assumption (from the deployment files, not from a live inspection).** No host port is published (`compose.yaml` has no `ports:`; `deploy/preflight.sh` and `verify.sh` refuse one), so nothing outside the VPS can reach `bft-web:3000` except through the tunnel. Inside the VPS, `bft-web` joins two external Docker networks: the tunnel's (`compass-tools_web` by default, which carries `cloudflared`) and the website-to-CRM API network. **Any other container attached to the same network can open `http://bft-web:3000` directly and send any `CF-Connecting-IP`/`CF-IPCountry`/`CF-IPCity` it likes.** In the CRM's release compose that includes the CRM application itself and its scheduled jobs. A forged value can (a) choose the rate-limit bucket (a fresh one per request), (b) be recorded as a lead's IP and approximate location (signed by the website and passed to the CRM as if it had come from the visitor). It cannot bypass CRM authentication or the signature check (the website signs with its own secret), and it cannot reach a third party. A client on the internet cannot do this. Not verified: the live VPS (which containers are on which network, whether any second route to the origin exists): that needs a read-only inspection on the server (runbook step 0), which was not done.

**What the code now offers (off by default).** Set `EDGE_PROOF_SECRET` (24 characters or more) and the Cloudflare headers are believed **only on a request that also carries the same value in the header `x-bft-edge-proof`**. A direct caller does not know the secret, so its forged headers are ignored: the request gets no trusted IP (it shares the one `unresolved` rate-limit bucket), no location, and no country hint. Details (`src/lib/client-ip.ts`):

* The comparison is constant-time (SHA-256 digests compared with `timingSafeEqual`); the secret is never logged and never part of a result.
* A secret that is **set but shorter than 24 characters fails closed** (nothing is believed): a guessable proof would be worse than none. `deploy/preflight.sh` refuses such a value before it can reach production.
* It only affects `TRUSTED_PROXY=cloudflare`. Empty or unset means off and every behaviour is exactly what it was.
* `X-Forwarded-For`, `X-Real-IP` and `Forwarded` are still never read in Cloudflare mode, with or without the proof.
* The same decision gates the IP captured for the CRM, the approximate location, the country hint (`/api/visitor-hint`) and the rate-limit key.

**Tests.** `tests/edge-proof.spec.ts` (11): off = unchanged; on without proof = forged IP, country and city ignored; wrong, near-miss, upper-cased, truncated and longer proofs refused; the right proof restores exactly the trusted behaviour; a too-short secret fails closed; Vercel and no-proxy modes unaffected; the secret never appears in a result; and on a real production server the hint and a real form submission (signed context received by a stand-in CRM) behave the same way. `tests/deploy-scripts.spec.ts` covers the preflight check.

**What you must do in production to use it (NOT done; needs your approval).**

1. In Cloudflare, add a request-header modification rule (Rules > Transform Rules > Modify Request Header) for this hostname that **sets** the static header `x-bft-edge-proof` to a long random value (set, not append, so a client-supplied header is overwritten). This is a Cloudflare change.
2. Put the **same** value in the website's `.env` as `EDGE_PROOF_SECRET`, and redeploy.
3. Verify with the runbook's real test submission that the stored IP is still the visitor's. **Order matters, and a mistake here is not harmless:** if the secret is set before the rule exists, every visitor is treated as unidentified, they all share the **one** `unresolved` rate-limit bucket, and the website's own allowance for the whole site becomes the single-client allowance (newsletter 6, contact 8, flight request 8 per 10 minutes in total, measured in `tests/rate-limit-topology.spec.ts`): after that, visitors are refused with the rate-limit message until the window passes. The CRM also records no visitor IP or location. So the rule must exist and be verified first (a request through the public hostname must reach the origin carrying `x-bft-edge-proof`), then the secret is set; to back out, empty `EDGE_PROOF_SECRET` and redeploy.
4. Rotation: change the value in Cloudflare and `.env` together; there is a short window in which requests are unidentified.

A network-level alternative (no code, no secret): give `bft-web` a tunnel network that only `cloudflared` joins, and a separate network for the CRM link. That changes the VPS topology and was not touched.
