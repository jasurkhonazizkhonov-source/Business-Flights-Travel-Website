# Departure airport from the visitor's device location

Implemented 2026-11-23 on top of release `c57eb51`. Local change, not committed, not deployed. Status of the checks: section 8. This document describes what the code does; where a claim is about a browser, it says so.

## 1. What changed, in one paragraph

The flight request form no longer has a "Use my location" button (nor its text, tooltip, placeholder space or "Location unavailable" label). Instead the browser is asked, once, for permission to use the visitor's location: when the **flight request page (`/flights`) opens**, or, on the **home page**, when the visitor **first uses the form** (a click, a tap or the keyboard arriving in any of its fields), so people who only look at the home page are never prompted. If they allow it, the nearest **major commercial airport** fills the **empty** From field, labelled "Suggested". If they decline, or no position can be had, nothing is suggested and nothing is said; the airport search works exactly as before. The earlier **network-derived** airport suggestion (an airport chosen on the server from Cloudflare's approximate position) was **removed**, because "declined means no suggestion" cannot hold while the network still suggests one: the server's hint now returns only a country code, for the phone prefix.

Decisions taken with the owner: the home-page prompt happens on first use, not on load (the form is mounted on two pages); the network airport is gone.

## 2. Behaviour by situation

| Situation | What the browser does | What the page does |
|---|---|---|
| Permission granted earlier | no prompt | fills From silently |
| Permission not yet decided | shows its own prompt (the page cannot influence or bypass it) | fills From if the visitor allows; otherwise as "denied" |
| Visitor declines (or dismisses) the prompt | remembers a refusal; a dismissal may be asked again on a later page load | From stays empty, no message; **no second question in this page session** (an in-memory flag, nothing stored) |
| Already blocked in browser settings | reports `denied` through the Permissions API | **no request is made at all**; From stays empty |
| No Geolocation API | - | From stays empty; no error |
| No Permissions API (older browsers) | - | the position is requested directly, once |
| Position unavailable, or the 8 s time-out | - | From stays empty; no error page, no message with the browser's error text |
| Position too imprecise (the browser reports an uncertainty above 100 km) | - | ignored |
| Invalid coordinates, or no major airport within 400 km | - | From stays empty |
| The visitor has chosen an airport, or typed anything in From, before the result arrives | - | the result is **ignored** (however late) |
| The nearest airport equals the chosen destination | - | not placed |
| The form re-renders, changes trip type, adds legs, or the page changes client-side | - | the question is never repeated (once per mounted form; and never after a refusal in this page session) |

Focusing the From field is **not** an edit: on the home page the focus is what triggers the question, and the answer still fills a still-empty field. Typing, or choosing an airport, is.

## 3. Which airport

`src/lib/airport-suggestion.ts` + `src/data/airport-hubs.json` (generated by `scripts/build-airport-hubs.mjs` from the application's own airport data): 1,167 large-class commercial airports only. The suggestion is the **nearest** by great-circle distance within **400 km**; none beyond that. A position beside a small airfield therefore gets the big airport (tested: Egelsbach, a general-aviation field, gets Frankfurt). The airport's name, city and country come from the full airport dataset, so what appears is exactly what the airport search would have offered ("City (IATA)"), and the submitted airport is checked again on the server against that dataset. "Nearest" is distance, not travel time or the best connections: that is why it is only ever a suggestion.

## 4. Privacy and security

* **Coordinates:** exist only inside `useDeviceAirport` in the visitor's browser, long enough to pick the airport. They are not written into the page, a URL, the console, any storage, any analytics (there is none), any request, the CRM, or the notification e-mail. Errors from the browser are never shown or logged. Tests assert each of these.
* **Storage:** unchanged: one `localStorage` key (the cookie-notice choice), no cookie, no session storage. The "refused" memory is a JavaScript variable.
* **Network:** no third-party geolocation or map service. The Geolocation API is the browser's own; the `Permissions-Policy` header allows `geolocation` for this site's own pages only (`geolocation=(self)`).
* **Server hint:** `GET /api/visitor-hint` returns `{"countryCode":"XX"}` and nothing else (no airport, city, coordinates or IP), is `private, no-store`, is rate-limited, and answers only behind the trusted proxy. The CRM's IP and approximate-location capture is **unchanged** and independent of this feature.
* **Hostile input:** a (compromised or old) server answer that still contains an airport is ignored; markup in an answer is never parsed.
* **Privacy page:** the paragraph on suggestions was rewritten to say this. It is marked for counsel's review in `PRODUCTION_REDEPLOYMENT_READINESS.md`.
* **Desktop and mobile:** both use the same browser API and the same prompt; behaviour was tested at 320, 375, 390 px and desktop, and with the browser's real geolocation emulation as well as scripted outcomes.

## 5. Accessibility

The label row holds the visible "Suggested" tag (`aria-hidden`) and a **polite status region** that exists, empty, before anything changes, and then says "Departure airport set to Munich (MUC) from your device's location. You can change it." (the input's `aria-describedby` points at it). Nothing focusable was added to the label row, so the tab order is that of the field itself. A refusal or failure is deliberately **not announced** (nothing changed for the visitor). Automated axe checks (WCAG 2.2 A/AA) pass with the suggestion showing; **no manual screen-reader test was done**, so how real assistive technology voices the status is unverified.

## 6. Layout

The "Suggested" tag appears in the From label row. Between 640 and about 670 px the From column is too narrow for the label and the tag, so the row would wrap and move the form 16 px; the row reserves two lines for 640-689 px, and everywhere else it stays one line. Measured at 10 px steps from 300 to 1500 px, and by `tests/layout-stability.spec.ts` at 31 widths: the To field and the submit button never move when the airport is filled.

## 7. Known limitations

1. **The prompt belongs to the browser.** Chrome and Edge may show a quiet indicator instead of a dialog after repeated dismissals; Safari and Firefox word and place it differently; a visitor who dismisses (rather than refuses) may be asked again on a later page load, because the browser stores nothing for a dismissal and this site stores nothing either.
2. A prompt on page open is a visitor-experience trade-off the owner chose for `/flights`: some visitors will decline reflexively. The home page asks later, on first use, for that reason.
3. Desktop browsers often derive the "device" position from the network (Wi-Fi/IP), so on a desktop the airport can be the wrong city's; the 100 km accuracy cut-off and the 400 km limit bound the damage, and it is a changeable suggestion.
4. Once the visitor allows location, the browser downloads the hub list (14 KB gzip) and the full airport dataset (258 KB gzip) to name the airport; the airport search downloads the same dataset the first time the visitor types. Embedding name/city/country in the hub file would avoid that (about 40 KB raw more in a file that is now 28 KB): not done, because it was not requested and has not been measured.
5. The suggestion is distance, not the best airport for the traveller.

**A flaky test, its cause and the fix (test-only).** `phone-validation-loading.spec.ts` ("a submit before the library has loaded...") failed on its first attempt on the phone projects in the whole run, and reproduced in isolation only with three parallel workers (about 1 in 100 runs; 2 of 5 stress iterations of 210 runs failed). It is **not** caused by the device-location code or by phone validation: traces of the failing runs show `ChunkLoadError ... ERR_FAILED`. The spec's own network handler (`page.route`) fetches every JavaScript chunk through Playwright's HTTP client and, if that fetch failed once (a reset keep-alive connection under load), **aborted** the chunk, so the page that needed it never hydrated and the test timed out 30 s later. Fix, in the spec only: the helper retries the fetch once and, if it still fails, lets the browser load the chunk itself instead of aborting it (the one chunk the "can never be loaded" test breaks on purpose is still aborted). Result after the fix: 5 stress iterations x 210 runs on the phone projects (1,050 runs), 3 workers, no retries: 1,050 passed; 70/70 on Desktop Chrome; the five width suites above (which contain the fixed spec) 0 flaky. The application code was not changed for this.

**Disclosure about the verification runs.** My verification script was started twice by mistake and the two invocations overlapped for part of the time: their summary lines were interleaved, and two width suites that start a server on a fixed port (`http-boundaries.spec.ts`, port 3253) collided (one "server exited before it was ready", one hook time-out), and one attempt of the 1024 px suite reported a failure plus 6 tests that did not run. Those overlapped attempts' logs were overwritten and are **not** counted as results above; all five width suites were then rerun one after another with nothing else running (the table above), and the Infrastructure project, run once, passed 208/208 with no flaky test. A separate session was also running the CRM's unit tests on the same machine during part of this time.

**Not tested:** Firefox and Safari (the Geolocation prompt and its remembered refusal behave differently; only Chromium was run), a real phone or a real GPS/Wi-Fi position, manual screen-reader use (so how real assistive technology voices the status message is unverified), the live CRM contract (needs a non-production CRM), and field performance data.
